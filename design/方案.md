# ReedRelay 产品与实施方案

> 2026-09-29 更新：用户已选择 A「谱台」，授权在 https://github.com/hyt0019/reed-relay 开发并按阶段自动提交、推送。以下要求作为实现与验收依据；完成情况持续记录于 docs/PROGRESS.md。

## 本轮确定的实现要求

- 采用 A 方案冷纸色、蓝墨按钮和清楚的曲谱/按键分区；听谱和风箱是两个独立入口。
- 默认使用截图的 Z/X/C/V/B/N/M/逗号，以及鼠标左/中/右键；全部支持用户自定义。
- 新增**调音与场景配置**：基准 A4 频率、基础音区、各音符的实际 MIDI 音高、修饰音程、启用的修饰组合均可调整；支持参考音试听、麦克风测音及从录音测音、音分偏差显示。配置可命名、保存、导入、导出，适配不同游戏或乐器场景。
- 为便于初次使用，提供明确标记为“待校准”的 C4–C5 基础模板与 -12/+1/+12 半音修饰假设。它们是可改的调音起点，不是从截图确认的真实音高。预演可直接使用，真实演奏前须确认配置。
- 本地“样例文件”中的 MP3 用于真实解码、全曲转写和结果检查；音频及其派生谱不上传 GitHub，仓库提供原创合成测试音和自制曲谱。
- 每完成一个下述阶段，先完成对应检查，更新进度记录，再提交并推送 main。网络直连失败时使用可用代理，不改变用户的全局网络配置。

### 本轮推送节点

1. 方案、仓库结构和进度清单。
2. 共享曲谱、校验、原调导出、调音配置与映射检查。
3. 可独立运行的风箱：A 界面、播放列表、热键、窗口守卫、鼠标长按、预演及调音界面。
4. 可独立运行的听谱：音频解码、Basic Pitch 转写、主旋律提取、校对与撤销、试听、JSON/MIDI/简谱导出。
5. 样例 MP3 全曲验证、界面截图检查、安装/启动脚本、独立打包配置、文档及剩余限制记录。

可选的 Demucs 分离和 MusicXML/PDF 排版作为后续扩展；本轮交付完整的音频转谱、校对、调音与演奏流程，不将可选模型的安装作为运行前提。游戏内真实发音及保护机制兼容性需要用户现场验证，其他功能在本地完成可复现检查。

## 1. 目标与边界

做两个可独立启动的 Windows 桌面程序：**听谱**负责把音频转成可校对、可导出的曲谱；**风箱**负责读取曲谱并在游戏前台按时间发送口琴按键。二者共享一种公开、可读的曲谱文件格式，但风箱不需要安装或运行听谱，听谱也不需要连接游戏。

目标是保留源音高和节奏，**默认不移调、不偷偷改八度、不丢弃无法演奏的音**。任意混音 MP3 无法保证完全准确的自动扒谱，单音口琴也无法同时复现所有和弦。因此软件输出两层结果：

1. **原始转写谱**：保留识别到的各声部音符、绝对音高、起止时间、力度与置信度；允许人工改错。
2. **游戏演奏方案**：依据当前键位和游戏音域，把可演奏音符映射为键盘与鼠标事件；冲突音、音域外音和不确定音显式标记，并让用户选择主旋律、保留某声部或手工处理。任何简化都只作用于演奏方案，原始转写谱不被覆盖。

## 2. 从截图得到的初始键位模型

| 游戏内显示 | 默认输入 | 处理方式 |
|---|---|---|
| `1 2 3 4 5 6 7 i` | `Z X C V B N M ,` | 8 个基础音符键，均可重新绑定。 |
| 降调 / 半音 / 升调 | 鼠标左键 / 中键 / 右键 | 按住时改变发音，松开回到普通状态；支持自定义绑定。 |

截图**不能确定** `1` 对应的实际音高、三个修饰项分别改变多少半音，以及不同修饰项能否叠加。游戏配置向导会逐项校准“音高 → 键 + 修饰键”，并提供试音记录表；校准前不自动假定 C 调，也不输出未经验证的按键方案。默认键位仅是截图初值，所有键位、热键、歌曲目录与目标游戏窗口都可保存为配置档。

## 3. 曲谱转换器「听谱」

### 输入和工作流

- 拖入或选择 MP3、WAV、FLAC、OGG、M4A；批量导入后逐首处理。先解码为统一的内部 PCM 音频，解码失败时给出文件与原因。
- 模式：**主旋律优先**（默认）、**完整音符候选**、**选定声部**。混音歌曲可选源分离步骤，再选择人声、乐器等声部；分离是可关闭的耗时选项。
- 推断音符的音高、起点、终点与大致节拍；在时间轴上显示波形/音符，在简谱或钢琴卷帘中显示原音高。时间轴以毫秒级绝对时间保存，节拍/小节线只是辅助阅读，避免量化后破坏原节奏。
- 给低置信度、密集重叠音、疑似颤音/滑音、超游戏音域的片段上色。可循环试听、点击片段听原音、调整音高和时长、拆分/合并音符、撤销/重做，再重新评估可演奏性。
- 输出 `.reedscore.json` 作为两个模块的交换格式；另导出 MIDI 和可阅读的简谱。若用户需要五线谱打印，再增加 MusicXML/PDF 导出，不把它作为首版准确性的前提。

### 技术路线

- Windows 桌面界面：**PySide6 + Qt Quick/QML**，两个独立入口和可共用的设计组件。Qt 官方提供 Python 绑定与 Qt Quick 控件。[Qt for Python](https://doc.qt.io/qtforpython-6/)
- 基础转写候选：**Basic Pitch**。它支持常见音频格式、返回 MIDI 与音符事件，官方也说明其效果以单个乐器的录音为佳。因此混音不能只依赖一次模型输出。[Basic Pitch 官方仓库](https://github.com/spotify/basic-pitch)
- 可选声部分离：评估 **Demucs**，它可将歌曲分为人声、鼓、贝斯和其他声部；复杂伴奏中的旋律仍需人工校对。此功能可能带来较大的模型下载和较长处理时间，安装包与性能将在实现阶段实测。[Demucs 官方仓库](https://github.com/facebookresearch/demucs)
- 音频解码使用独立适配层；FFmpeg 可作为实现候选，具体打包方式与许可证在建仓时核对。转写模型与音频解码器都只属于听谱，不进入风箱的依赖链。

## 4. 自动演奏器「风箱」

- 独立打开 `.reedscore.json` 和播放列表；也可手工导入符合格式的第三方曲谱，不需要先启动听谱。
- 用户设置**启动/停止**、**上一首**、**下一首**三个全局热键；界面显示当前绑定，捕获新按键时立即检查重复绑定与系统冲突。预览图以 `F8 / F6 / F7` 示意，最终默认值可在首轮游戏实测后定。
- 提供单独的**紧急停止**热键。停止、切歌、游戏失焦、异常退出时立即释放所有由程序按下的键盘与鼠标按钮。切歌时停止旧曲，更新列表选中项；可配置是否自动从新歌开头继续。
- 使用高精度时钟按曲谱起止时间调度按下与松开事件。先按修饰键、再按音符键；换音时按游戏实测结果处理短间隔和键释放。速度倍率和启播延迟可调，原谱时间不随之改写。
- 用户选择目标游戏窗口，只有该窗口位于前台时才发送演奏按键；运行状态、当前音、歌曲进度与无法演奏片段清楚可见。提供不向游戏发送输入的预演模式，用来检查排程和键位。
- Windows 输入实现候选为系统 `SendInput`；其权限级别有限制，某些游戏可能拒绝模拟输入，需要以游戏实测确认。不会承诺绕过游戏保护机制。[Microsoft SendInput 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

## 5. 数据和模块划分

```text
reed-relay/
  apps/converter/       # 听谱独立入口、音频解码、模型推断、校对界面
  apps/player/          # 风箱独立入口、热键、排程、游戏输入、播放列表
  packages/score/       # 曲谱模式、校验、导入导出、版本迁移
  packages/ui/          # 可共用的主题色、图标与交互组件
  tests/                # 音高/时间、曲谱兼容、调度和按键释放测试
  docs/                 # 用户手册、键位校准、格式说明、截图
```

交换文件采用带版本号的 UTF-8 JSON；每个音符至少包含 `start_ms`、`duration_ms`、`midi_pitch`、`voice`、`confidence`，曲目包含源文件信息、调式估计和时间基准。若检测到微分音或滑音，保留附加音高偏移数据；游戏只支持离散音高时标记不可精确复现。播放方案单独存储配置档和映射版本，避免更换键位后篡改原谱。对非法时间、负时长、未知格式版本做明确报错。

## 6. 两个界面的关键交互

**听谱**：导入 → 选择识别模式 → 查看处理进度 → 波形与音符对齐校对 → 查看“低置信度/音域外/重叠音”列表 → 试听 → 导出。界面保持可取消、可撤销、可恢复工程；长时间运算在后台执行，不冻结窗口。

**风箱**：添加曲谱 → 选择游戏键位配置 → 测试按键映射 → 设置热键与目标窗口 → 在游戏中一键启动/停止、切歌。大字号状态、当前音高和醒目的紧急停止提示保证边游戏边看也能辨识。键位冲突、音域外音以及游戏失焦都给出明确原因和下一步操作。

三个视觉方向见同目录预览图：A「谱台」偏长期校谱；B「夜航控制台」偏游戏中使用；C「磁带录音室」更活泼。预览只代表视觉与布局方向，所有可点击控件尚未开发。

## 7. 实施顺序与验收

1. **确认游戏映射与原型**：记录 8 个基础音实际音高、三个鼠标修饰的音程、是否可叠加、长按时值和连音行为；根据选中的预览方向定稿两套界面。
2. **定义共享曲谱格式**：先做模式校验和样例文件，使转换器、演奏器可以分别开发和单独运行。
3. **完成听谱最小闭环**：导入音频、生成原调事件、时间轴校对、试听、导出。使用已知音高/时值的测试音频校验，不以“看起来像曲谱”作为准确性依据。
4. **完成风箱最小闭环**：导入手工样例曲谱、热键和键位配置、预演、游戏窗口前台守卫、启动停止切歌、释放所有按键。重点测试快速连续音、长音、切歌中止和失焦。
5. **整合与交付**：用真实音乐和真实游戏回归测试，形成 Windows 可运行发布包、README、安装/配置文档、演示录屏与 GitHub Release。听谱与风箱分别打包，风箱不携带音频模型。

验收关注三件事：**音高和事件时间是否与已知样本一致；谱中无法演奏的部分是否被完整标出；任何停止路径是否都能释放按键**。真实流行歌曲的转写结果由用户在校对界面确认，不能承诺对任意 MP3 全自动零误差。

## 8. 仓库命名与介绍

- 推荐仓库名：`reed-relay`。Reed 指口琴簧片，Relay 指从声音到谱、再到游戏输入的传递；英文短、便于输入，项目可用中文名「风箱 / 听谱」。
- GitHub 简介（中文）：`将音频转成保留原调的可编辑曲谱，并通过可自定义键位在游戏中自动演奏的双模块桌面工具。`
- GitHub description（英文，可二选一）：`Audio-to-score transcription and configurable in-game harmonica playback for Windows.`
- README 首页应展示两模块关系、支持格式、三步上手、键位校准、安全停止、准确性边界、两套程序独立启动方式、截图、许可与模型来源。

## 9. 开工前需要的资料

用户选定 A/B/C（或指定要混合的元素）及 GitHub 仓库地址后即可开始。为了避免把游戏音高猜错，首轮实现还需要游戏名称与版本、能否提供 8 个基础音和三个鼠标修饰的实录音或键位说明，以及游戏是否接受普通 Windows 模拟输入。缺少录音时可先完成转换器、格式、演奏器预演和校准向导，再在游戏现场完成映射。
